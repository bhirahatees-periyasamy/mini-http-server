# Specification 002 - HTTP Response

## Status

**Draft**

---

# Objective

Design the `Response` data model used by the HTTP server.

The `Response` struct represents an HTTP response generated by the application before it is serialized and written to a network stream.

This specification defines only the response model.

Serialization into the HTTP/1.1 wire format is covered in a separate specification.

---

# Motivation

Every request processed by the server produces a response.

A dedicated response model provides:

* Clear separation between application logic and networking.
* Type-safe representation of HTTP responses.
* Easier testing.
* Reusable response construction.

---

# Responsibilities

The `Response` type shall:

* Represent an HTTP response.
* Store the HTTP status code.
* Store response headers.
* Store the response body.

The `Response` type shall **not**:

* Serialize itself into HTTP.
* Write data to a socket.
* Perform routing.
* Read files.

---

# Expected Module

```text
src/http/response.rs
```

---

# Public API

The module shall expose:

```rust
pub struct Response;
```

Helper constructors may be added in future versions.

---

# Required Fields

The response model shall contain the following fields.

| Field   | Type                    | Description           |
| ------- | ----------------------- | --------------------- |
| version | Version                 | HTTP protocol version |
| status  | StatusCode              | HTTP response status  |
| headers | HashMap<String, String> | Response headers      |
| body    | Vec<u8>                 | Response body         |

---

# Invariants

A valid response shall satisfy the following rules.

* Every response has one HTTP version.
* Every response has one status code.
* The response body may be empty.
* Header names are unique.
* The body is stored as raw bytes.
* The response object represents application data only.

---

# Out of Scope

The following features are intentionally excluded.

* Header generation
* Content-Length calculation
* Chunked transfer encoding
* Compression
* Cookies
* Streaming responses
* Keep-Alive handling

These will be covered by future specifications.

---

# Example

Application response:

```text
Status: 200 OK

Headers:
Content-Type: text/plain

Body:
Hello World
```

Expected model:

```text
Response
├── version : HTTP/1.1
├── status  : OK
├── headers
│   └── Content-Type
└── body
```

---

# Error Handling

The response model itself should not fail.

Validation is performed by higher layers.

---

# Dependencies

The module may depend on:

* std::collections::HashMap
* http::status
* http::version

The module shall not depend on:

* TcpStream
* Router
* Filesystem
* Parser

---

# Unit Tests

The following behaviors should be tested.

## Create Response

Verify that a response can be constructed.

---

## Empty Body

Verify that empty responses are supported.

---

## Binary Body

Verify that arbitrary binary data can be stored.

Examples:

* PNG
* JPEG
* PDF
* ZIP

---

## Headers

Verify that headers are stored correctly.

---

## Status Codes

Verify that supported status codes can be represented.

---

# Acceptance Criteria

This specification is complete when:

* A `Response` struct exists.
* Required fields are implemented.
* Unit tests pass.
* No networking code exists inside the module.
* No serialization logic exists inside the module.

---

# Future Improvements

Future versions may include:

* Builder pattern
* Convenience constructors
* Automatic header generation
* Cookie support
* Compression metadata
* Response extensions

These features are intentionally excluded from Version 1.
